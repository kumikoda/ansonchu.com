Hardware · GPU programming, one level down TENSOR CORES & MMA

Inside the Tensor Core

The roofline lesson told you the GPU is a matmul machine starving for bytes. This lesson opens the machine. What exactly is a tensor core, what single instruction does all of deep learning compile down to, what number formats are actually moving through the wires — and why every workload ends up shaped as tiles.

01 The unit

What a tensor core actually is

A GPU's ordinary CUDA cores execute scalar ops — one fused multiply-add (FMA) on one pair of numbers per cycle. A tensor core is a different piece of silicon on the same SM: a small systolic-style array that performs an entire matrix multiply-accumulate (MMA) — D = A·B + C on a fixed small tile — as one instruction. NVIDIA introduced them in 2017 (Volta) as the answer to Google's TPU systolic arrays; the first generation handled only FP16 at a tiny 4×4×4 shape. Five generations on, they're the reason a GPU is "a matmul machine": on H100/B200, tensor cores deliver an order of magnitude more FLOPs than the CUDA cores beside them.

Ops, precisely When a datasheet says "FLOPs," the atom being counted is the FMA: a×b + c, two floating-point ops. A CUDA core does one per cycle. One tensor-core MMA instruction performs thousands — an m16n8k16 tile is 16·8·16 = 2048 multiply-adds — in a handful of cycles. Same atom, massively amortized instruction overhead. That amortization is the tensor core's advantage: fetch/decode once, compute a whole tile.

02 Who issues it

The warp: 32 threads acting as one

You don't program a tensor core from a single thread. The unit of execution is the warp — 32 threads that issue instructions in lockstep — and an MMA is a warp-cooperative op: all 32 threads participate simultaneously, each owning a deterministic slice of the A, B, and accumulator fragments in its registers (thread t holds specific rows/columns given by a fixed layout formula). The hardware gathers those register slices, feeds the array, and scatters results back.

How warps coordinate MMAs is what changed across generations. Hopper introduced wgmma — warp-group MMA, four warps (128 threads) cooperating on a big tile like m64n256k16. Blackwell's 5th-gen replaced it with tcgen05.mma: back to warp-level, independent issue, with each instruction completing in a near-constant ~11 cycles regardless of tile size or precision — versus 32–128 cycles for wgmma's warp-group barriers, a 2.9–11.6× latency drop. Blackwell also added TMEM, a dedicated tensor memory on the SM, plus paired-CTA execution across two SMs, to keep the array fed without hammering shared memory.

03 What numbers move

The precision ladder — and why it keeps descending

The numbers flowing through the wires have been shrinking for a decade, because of the roofline: halve the bits and you double both the effective bandwidth and the FLOPs (more subword lanes through the same silicon). The current ladder, all supported natively in Blackwell's unified pipeline:

Two details make the low end livable. First, mixed precision: inputs can be FP8/FP4 but accumulation stays FP32 (the f32.…​.f32 in the instruction) so error doesn't compound across the K dimension. Second, block scaling: naked FP4 (e2m1 — 16 values!) is useless alone, so NVFP4 attaches an FP8 scale factor to every block of 16 FP4 elements, plus a per-tensor FP32 scale — microscaling that lets each small block use its full dynamic range. That's the trick behind FP4 hitting ~7,700 TFLOPS on Blackwell and behind the first credible FP4 pretraining recipes.

Thread to your stack This ladder is the mechanism under three earlier lessons at once: quantization (serving models in INT4/FP4 = moving fewer bytes past the memory wall), tokens-per-watt (fewer bits per op = more ops per joule), and hardware↔model co-design (FP8/FP4 exist because transformers tolerate them; models now train targeting them). Precision is the currency both sides negotiate in.

04 Shape of the workload

Everything becomes tiles

Why do instructions come in shapes like m16n8k16 at all? Because the entire GPU programming model is hierarchical tiling of one big GEMM. A transformer layer is a handful of large matmuls (QKV projections, attention scores, the MLP pair — this is why the silicon went matmul-native). Each big GEMM is carved into thread-block tiles staged in shared memory, those into warp tiles in registers, and those into the MMA-shaped fragments the tensor core eats. And the workload's outer shape decides everything Whether all this silicon is even busy depends on the shape of the outer GEMM. Prefill multiplies (many tokens × weights) — big M, tiles everywhere, compute-bound, tensor cores saturated. Decode multiplies (1 token × weights) — M=1, a matrix-vector op that can't fill tiles, so it's memory-bound and the tensor cores idle. One instruction set, two regimes — the entire prefill/decode disaggregation story from your inference-engines lesson is downstream of tile geometry.

Q1 What distinguishes a tensor core from an ordinary CUDA core?

Amortized instruction overhead. A CUDA core does one fused multiply-add per cycle. A tensor core is separate systolic-style silicon that computes a whole MMA tile per instruction — m16n8k16 alone is 2048 multiply-adds — introduced in Volta (2017) as NVIDIA's answer to the TPU. That's why tensor cores deliver an order of magnitude more FLOPs than the CUDA cores next to them.

Q2 In mma.sync.aligned.m16n8k16.f32.f16.f16.f32, what do the two parts mean?

Shape + precision recipe. M×N×K defines the fragment dimensions the warp processes (16×16 times 16×8, accumulated into 16×8). The type string reads D,A,B,C: FP16 inputs, FP32 accumulator/output — mixed precision, so tiny formats can feed the array while sums stay accurate across the K dimension. All 32 threads of one warp hold fixed slices of these fragments and issue together.

Q3 Why does halving precision (FP16→FP8→FP4) keep paying off, and what makes bare FP4 usable?

The roofline pays twice. Fewer bits per number means more numbers per byte moved (memory wall) and more subword lanes through the same silicon (FLOPs) — FP4 hits ~7,700 TFLOPS on Blackwell. Naked e2m1 FP4 has only 16 representable values, so NVFP4 microscales it: each block of 16 elements shares an FP8 scale factor, with a per-tensor FP32 scale on top, letting every block use its full range. FP32 accumulation keeps the sums honest.

Q4 What changed between Hopper's wgmma and Blackwell's tcgen05.mma?

Dispatch granularity. Hopper's wgmma made four warps (128 threads) cooperate on big tiles, paying warp-group synchronization: 32–128 cycles depending on shape. Blackwell's tcgen05.mma issues at warp level with ~11-cycle latency nearly independent of tile size or precision, adds dedicated TMEM on the SM, and can pair CTAs across two SMs — keeping the bigger 5th-gen array fed.

Q5 Why is decode memory-bound while prefill saturates the tensor cores, in tile terms?

Tile geometry is destiny. The tensor core wants fat M×N×K tiles it can reuse from fast memory. Prefill's batch-of-tokens GEMM provides them — compute-bound, array saturated. Decode's one-token step degenerates to matrix-vector: you still stream every weight byte from HBM but present no tile to fill, so arithmetic intensity collapses. That's the mechanical root of prefill/decode disaggregation from the inference-engines lesson.
Takeaway

A tensor core is silicon that eats one instruction — D = A·B + C on a fixed tile like m16n8k16 — issued by a 32-thread warp, with thousands of multiply-adds amortized per issue. The numbers in the wires keep shrinking (BF16 → FP8 → NVFP4 with block scaling) because fewer bits mean more bandwidth and more FLOPs, while FP32 accumulation keeps sums honest. And every workload is tiled to feed it: big-M GEMMs saturate the array, M=1 decode starves it. The whole stack — quantization, FlashAttention, prefill/decode splits — is downstream of this one unit's geometry.
