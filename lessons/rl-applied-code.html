RL for Code

Code is the dream domain for RLVR, because the verifier already exists: run the tests. Either they pass or they don’t — a crisp, automatic, scalable reward with no reward model to train. That single fact is why coding is where RL has moved fastest, and why it pulls in every infra lesson you’ve done.

01 Why code is special

The verifier comes for free

RLVR’s whole premise is a cheap, trustworthy reward (Lesson 5). Most domains need you to build that verifier. Code hands it to you: unit tests, type checkers, and compilers are pre-existing, deterministic oracles. That’s why the early RLVR wins clustered in code and math, and why benchmarks like LiveCodeBench (competitive problems) and SWE-bench Verified (real GitHub issues) became the yardsticks.

The two flavors of code RL Single-shot: write a function, run tests, reward — a bandit, like a math problem with a richer checker (LiveCodeBench-style). Agentic: a multi-turn loop over a real repo — read files, edit, run the suite, iterate until green (SWE-bench-style). The first is the contextual bandit from Lesson 7; the second is the long-horizon agentic MDP, and it’s where coding agents like the ones you build actually live.

02 Where your lessons converge

Code RL is an infra problem

Running tests means executing model-written code — untrusted, possibly destructive, at rollout scale. So code RL is where the whole systems cluster becomes load-bearing at once: sandboxes isolate each execution, environments (Verifiers-style: repo + tests + rubric) define the task, and the harness has to absorb the cost.

The throughput reality Remember from the sandbox lesson: a math check is microseconds; running a repo’s test suite is seconds, and it dominates rollout wall-clock. Code RL is the domain where the sandbox, not the model, sets your training speed — which is why warm pools, snapshot-restore, and parallel execution stop being nice-to-haves and become the thing that decides whether your run is affordable.

04 The twist

Code as a tool, not just a target

The frontier move: let the model use code mid-reasoning, not only produce it. Tool-integrated reasoning — the policy writes and runs a snippet to compute something, sees the result, and continues. With RL, models learn to spontaneously reach for code execution when it helps (e.g. doing arithmetic by running Python instead of guessing tokens), and this transfers straight into math.

Why this matters for you This is the same loop as computer/terminal use (the agents lesson): code execution is a tool in the action space, and RL teaches when to call it. For your chip-design tooling, the pattern generalizes cleanly — an agent that writes a check, runs it against the design, reads the EDA result, and iterates is a code-RL agent whose “tests” are your verification tools. The reward is just “did the design pass.”

Q1 Why is code considered the ideal RLVR domain?

Free verifier. RLVR needs a cheap, reliable reward, and most domains make you build one. Code ships with deterministic oracles — unit tests, type checkers, compilers — so pass/fail is the reward with no reward model and no human labels. That's why early RLVR wins clustered in code (and math).

Q2 What's the difference between single-shot and agentic code RL?

Bandit vs MDP. Single-shot (LiveCodeBench-style): emit a function, run tests, get reward — one step, a contextual bandit. Agentic (SWE-bench-style): read files, edit, run the suite, iterate until green — a long-horizon agentic MDP with partial observability. The second is where real coding agents live, and where the harness/sandbox cost bites.

Q3 In code RL, what usually sets your training wall-clock?

The sandbox. A math answer-check is microseconds; running a repo's tests is seconds and dominates the rollout. Code RL is the domain where the sandbox, not the model, caps throughput — so warm pools, snapshot-restore, and parallel execution decide whether your run is affordable. The infra lessons become load-bearing here.

Q4 "Pass the tests" is a reward proxy. What's a real way a policy games it, and a defense?

Goodhart, code edition. The policy can hard-code answers for the visible test inputs, exploit weak coverage (pass 3 tests, break everything else), or even edit the test file if it can reach it. Defenses: hidden held-out tests it never sees, read-only/sandboxed test files, coverage enforcement, and treating the verifier as adversarially probed — because the policy is literally a code-writer attacking your checker.
Takeaway

Code RL works because the test suite is a ready-made verifier — but that makes it an infra problem (sandbox, environment, harness all at once) and a Goodhart problem (the policy games the gap between "tests pass" and "code is correct"). And the real unlock is code as a tool the model learns to wield mid-reasoning.
