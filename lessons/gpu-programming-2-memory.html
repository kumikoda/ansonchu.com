The Memory Model: Feeding the Beast

Chapter I ended with a verdict: the naive matmul is doomed at 0.25 FLOP/byte. This chapter is the acquittal. Coalescing (how a warp's loads become transactions), shared memory (the cache you manage, and its bank traps), the full tiled matmul with its arithmetic-intensity math, and the modern async machinery — cp.async, TMA, double buffering — that top kernels are built on.

01 The terrain

The hierarchy, with numbers you should memorize

Each level is roughly an order of magnitude in latency and capacity. The craft of GPU programming is almost entirely this: move data up the hierarchy once, then reuse it as many times as possible before it falls back down. Registers and shared memory are the only levels you control explicitly — and they're where every fast kernel lives.

02 Global memory

Coalescing: a warp's loads become transactions

Here's the mechanism most people never learn precisely. When a warp executes a load, the hardware doesn't perform 32 separate loads — it looks at the 32 addresses, determines which aligned 32-byte sectors (grouped into 128-byte cache lines) they touch, and issues one memory transaction per distinct sector. The efficiency of your kernel's memory system is simply: bytes you asked for ÷ bytes the transactions moved.

// warp of 32 threads, 4-byte floats
x = A[threadIdx.x];          // addresses 0,4,8,…,124 → ONE 128B line. 100% efficiency
x = A[threadIdx.x * 32];     // addresses 0,128,256,… → 32 separate sectors.  ~3%   
x = A[rand()];               // scattered → up to 32 transactions, mostly wasted bytes

The strided case is the silent killer because it looks innocent in source. Its most common disguise is the array-of-structs:

// AoS: each thread reads .x → addresses stride by sizeof(Particle)=32B
struct Particle { float x,y,z,vx,vy,vz,m,pad; };
float xi = p[i].x;                       // warp touches 32 different lines for 128 useful bytes

// SoA: all x's contiguous → one line per warp. Same data, 8× less traffic
struct Particles { float *x,*y,*z,*vx,*vy,*vz,*m; };
float xi = P.x[i];
The rule, and where you've seen it Consecutive threads should touch consecutive addresses. Note the subtlety: it's across threads at one instant, not along one thread's loop. This is also why row-major matmul reads of B[k*N + col] in Chapter I were actually fine (threads vary col → contiguous) while a transposed access pattern would have been catastrophic — and why real frameworks obsess over tensor layout (NCHW vs NHWC) — it's coalescing all the way down.

03 Shared memory

The cache you manage — and its 32 banks

Shared memory is on-SM SRAM you allocate explicitly (__shared__), visible to all threads of a block, living exactly as long as the block. It's the physical substrate of cooperation: threads stage data there, synchronize with __syncthreads() (a block-wide barrier: everyone arrives before anyone proceeds), then read each other's contributions at ~100× HBM speed.

Its one trap: the SRAM is physically 32 banks, each serving one 4-byte word per cycle, with address→bank mapping bank = (addr/4) % 32. If the 32 threads of a warp hit 32 different banks, everything is serviced in one cycle. If k threads hit the same bank (different words), the accesses serialize into k cycles — a bank conflict. (Exception: all threads reading the same word is a free broadcast.)

__shared__ float tile[32][32];
x = tile[threadIdx.x][0];    // column read: addresses stride 32 words → (i*32)%32 ≡ bank 0
                             // ALL 32 threads on one bank → 32-way conflict, 32× slower

__shared__ float tile[32][33];   // the classic fix: pad the row by ONE word
x = tile[threadIdx.x][0];    // stride 33 → (i*33)%32 = i → 32 distinct banks. conflict-free

That [32][33] padding trick — burn 3% of the space, break the stride's alignment with the bank count — appears in virtually every transpose and tiled kernel ever written. Newer alternatives (xor-swizzling the index) achieve the same de-aliasing without wasting the space, and are what CUTLASS generates.

04 The payoff

Tiled matmul, in full — fixing Chapter I's crime

Now assemble everything. The naive kernel's sin was that each thread privately re-fetched rows and columns from HBM that its blockmates were fetching too. The fix: the block cooperatively loads a TILE×TILE patch of A and of B into shared memory (coalesced!), everyone computes against the staged tiles, and the block slides along the K dimension in phases.

#define TILE 32

__global__ void matmulTiled(const float* A, const float* B, float* C, int N) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];      // (pad to [TILE][TILE+1] if you'll read columns)

    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.f;

    for (int ph = 0; ph < N / TILE; ++ph) {          // slide along K, one tile per phase
        // cooperative, COALESCED load: each thread brings one element of each tile.
        // threadIdx.x varies fastest and indexes the contiguous dimension of both. ✓
        As[threadIdx.y][threadIdx.x] = A[row * N + (ph*TILE + threadIdx.x)];
        Bs[threadIdx.y][threadIdx.x] = B[(ph*TILE + threadIdx.y) * N + col];
        __syncthreads();                              // tiles fully staged before anyone computes

        #pragma unroll
        for (int k = 0; k < TILE; ++k)
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];   // SMEM reads, not HBM
        __syncthreads();                              // don't overwrite tiles others still read
    }
    C[row * N + col] = acc;      // (bounds checks elided for clarity)
}

Now the audit that matters. Per phase, the block loads 2·TILE² floats from HBM and computes 2·TILE³ FLOPs against them. Arithmetic intensity:

AI = 2·TILE³ FLOPs / (2·TILE² · 4 bytes) = TILE / 4   FLOP per byte
naive:      0.25          (each element fetched N times)
TILE = 32:  8.0           — 32× less HBM traffic, 32× higher AI

Every element now enters the SM once per tile-row of blocks instead of once per thread, and is reused TILE times from SMEM. The general law: AI grows linearly with tile size — which is the entire reason Chapter III's tensor cores want the biggest tiles that fit, why register-level sub-tiling (each thread computing a small block of C from registers, not one element) pushes AI further, and why the memory hierarchy and the tiling hierarchy are the same picture. This kernel structure — stage, sync, compute, sync, slide — is the skeleton inside every GEMM library and FlashAttention (whose innovation was applying it to attention: never materialize the N×N score matrix in HBM; keep tiles of it in SMEM with an online softmax).

Also new here: cooperation via warp shuffles For reductions (sums, maxes — softmax's other half), threads within a warp can skip SMEM entirely and exchange registers: val += __shfl_down_sync(0xffffffff, val, 16); …8; …4; …2; …1; reduces 32 values to one in 5 steps with zero memory traffic. Idiomatic reductions do warp-shuffle first, then one SMEM step across the block's warps. Registers > SMEM > HBM — always solve at the highest level you can.

05 The modern layer

Overlap: async copies, TMA, double buffering

The tiled kernel still has a rhythm flaw: during each load phase the math units idle, and during math the memory system idles. The fix is the same idea as the warp scheduler's, applied inside one block — overlap — and modern hardware gives it first-class machinery:

cp.async (Ampere): threads issue global→shared copies that proceed in the background, without staging through registers, while the warp keeps computing. TMA (Hopper/Blackwell — the Tensor Memory Accelerator): a dedicated engine that transfers whole multi-dimensional tiles between HBM and SMEM from a descriptor — one thread kicks off the copy of an entire tile, hardware generates every address, and completion signals an mbarrier. Address-generation arithmetic leaves the SM entirely.

// double buffering: compute on tile[cur] while TMA/cp.async fills tile[nxt]
__shared__ float As[2][TILE][TILE], Bs[2][TILE][TILE];
load_async(As[0], Bs[0], phase=0);                // prime the pipeline
for (int ph = 0; ph < N/TILE; ++ph) {
    int cur = ph & 1, nxt = cur ^ 1;
    if (ph+1 < N/TILE) load_async(As[nxt], Bs[nxt], ph+1);   // fetch ahead
    wait_for(cur);                                // barrier only on the buffer we need
    compute_on(As[cur], Bs[cur]);                 // math overlaps the nxt fetch
}

Take it one step further and you get warp specialization, the architecture of Hopper/Blackwell-era kernels (CUTLASS, FlashAttention-3): dedicate producer warps to driving TMA and consumer warps to driving the tensor cores, coordinating through those mbarriers — a hardware-level actor pipeline inside a single thread block. The SM becomes a tiny factory: one crew hauls tiles, one crew does math, nobody waits.

Q1 What does "coalescing" actually mean at the hardware level?

Transactions, not loads. Efficiency = bytes requested ÷ bytes moved. A warp reading A[tid] touches one 128B line (100%); A[tid*32] touches 32 sectors for the same 128 useful bytes (~3%). The rule — consecutive threads, consecutive addresses — is about the warp at one instant, not one thread's loop, and it's why SoA layouts beat AoS and why frameworks obsess over tensor memory layout.

Q2 Why does tile[32][33] (padding by one) fix the column-read bank conflict?

Break the stride's alignment with the bank count. Banks serve one 4B word per cycle each. Stride-32 word accesses all land on bank 0 → 32-way conflict → 32× slowdown. Making rows 33 words long shifts each row's start by one bank, so a column walk visits all 32 banks. Swizzling (xor-ing index bits) achieves the same without the 3% space cost — it's what CUTLASS emits. Same-word reads are a free broadcast, not a conflict.

Q3 In the tiled matmul, what's the arithmetic-intensity math per phase?

Reuse is the whole game. The block cooperatively stages TILE×TILE patches of A and B (2·TILE²·4 bytes of HBM traffic) and computes 2·TILE³ FLOPs against them — each staged element reused TILE times from SMEM. AI = TILE/4 grows linearly with tile size, which is why bigger tiles (and register sub-tiling, and tensor-core-sized fragments) keep winning, and why FlashAttention is this same discipline applied to attention scores.

Q4 Why are there two __syncthreads() per phase in the tiled kernel?

Two hazards, two barriers. Without the first, a fast thread computes against a half-loaded tile (read-before-write). Without the second, a fast thread starts phase ph+1's load and clobbers SMEM a slow thread is still reading from phase ph (write-before-read). __syncthreads is block-scope only — which is also a reminder that cross-block coordination doesn't exist mid-kernel (Chapter I). Double buffering replaces barrier 2 with per-buffer mbarriers so the overwrite hazard disappears entirely.

Q5 What do warp shuffles (__shfl_down_sync) buy you in a reduction?

Registers > SMEM > HBM. Shuffle instructions move values lane-to-lane inside a warp without touching memory at all — log₂(32)=5 steps for a full warp reduction. The pattern (warp shuffle, then a small shared-memory combine across the block's warps) is the skeleton of every fast sum, max, and softmax denominator. Solve at the highest hierarchy level available.

Q6 What is TMA, and what does warp specialization make of it?

A DMA engine for tiles, and a factory around it. TMA moves multi-dimensional tiles autonomously — address arithmetic leaves the SM, one thread triggers the copy, completion posts to an mbarrier. Built on cp.async's background-copy idea, it enables clean double buffering, and warp specialization (producers haul tiles, consumers run MMAs, coordinating via barriers) is the architecture of CUTLASS and FlashAttention-3 era kernels: an actor pipeline inside one block.
Takeaway

Fast GPU code is one discipline applied at every level: coalesce your way into the chip (warp addresses → transactions), stage what you'll reuse in shared memory (minding the 32 banks), audit reuse as arithmetic intensity (tiling makes AI grow linearly with tile size — 0.25 → 8.0 FLOP/byte in one kernel), reduce in registers when you can, and overlap everything with async copies, TMA, and double buffering until no unit ever waits. That skeleton — stage, sync, compute, slide — is inside every GEMM library and FlashAttention itself.
