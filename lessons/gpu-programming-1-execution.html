The Execution Model, From First Principles

This is the technical series. No hand-waving: by the end of this chapter you'll know exactly what happens when a kernel launches — what a thread, warp, block, and grid physically are, why the GPU hides latency instead of avoiding it, what code the machine really executes, and you'll have read every line of two real kernels. Chapter II does the same for memory.

01 First principles

A latency machine vs a throughput machine

Start from the design question, because everything downstream follows from it. A CPU is built to finish one instruction stream as fast as possible. It spends the overwhelming majority of its die on machinery that serves that goal: big caches so loads rarely miss, branch predictors so pipelines rarely stall, out-of-order engines to find parallelism inside a single thread. The actual arithmetic units are a small fraction of the silicon.

A GPU inverts the bet. It accepts that any individual thread will run slowly — a global memory load takes hundreds of cycles and the GPU does almost nothing to hide that from the thread — and instead spends the die on thousands of arithmetic lanes plus enormous register files. The strategy: when one group of threads stalls on memory, instantly switch to another group that's ready. Latency isn't avoided; it's hidden under other threads' work. This only works if you give the machine vastly more parallel work than it has lanes — oversubscription is the fuel.

The physical machine: an array of SMs

Concretely, an H100 is 132 Streaming Multiprocessors (SMs) sharing a ~50 MB L2 and HBM. Each SM contains four warp schedulers (each issuing one instruction per cycle for one warp), 128 FP32 lanes ("CUDA cores"), 4 tensor cores, a 256 KB register file, and 228 KB of combined shared memory/L1. Two numbers to internalize: each SM can host up to 64 resident warps (2,048 threads) simultaneously, and the register file is so large because every resident thread's registers stay allocated the whole time — that's what makes switching between warps free. The GPU-wide picture: 132 SMs × 2,048 threads ≈ 270K threads resident at once, with millions more queued.

02 The execution unit

SIMT: the warp is the real machine

Here's the part the marketing hides: the GPU does not execute 2,048 independent threads per SM. The hardware unit of execution is the warp — 32 threads that share one instruction stream. A warp scheduler picks a warp, issues one instruction, and all 32 lanes execute it on their own data. This model is called SIMT (Single Instruction, Multiple Threads): you write code as if each thread were an independent scalar program, but the machine runs it 32-wide, like SIMD with the vectorization done by the hardware instead of the compiler.

The abstraction leaks in exactly one place, and it's the most important performance rule in this chapter: branch divergence. If threads within one warp take different sides of a branch, the warp cannot execute both sides at once — it runs the if path with the else threads masked off (their lanes idle), then the else path with the if threads masked. Worst case, a 32-way divergent branch runs at 1/32 of throughput.

// Divergence is about *which threads* differ, not the branch itself.
if (threadIdx.x % 2 == 0) { ... }   // TERRIBLE: every warp splits 16/16 — both paths serialized
if (threadIdx.x < 64)      { ... }   // FINE: warps 0-1 all-true, warps 2+ all-false — no split
if (blockIdx.x == 0)       { ... }   // FREE: whole blocks agree; a warp never disagrees internally
Two refinements worth knowing For short branches the compiler often uses predication — both paths execute with results masked, no actual branch — which is why tiny ifs are cheap. And since Volta, each thread has its own program counter (independent thread scheduling), which fixes old deadlock patterns and enables per-thread progress, but does not change the economics: divergent lanes still idle. Correctness got per-thread; performance is still per-warp.

03 The software model

Kernels, grids, blocks — and why the hierarchy exists

A kernel is a C++ function marked __global__ that you launch as N copies running in parallel — one per thread. You organize those N threads in a two-level hierarchy: threads are grouped into blocks (up to 1,024 threads each), and blocks form the grid. The launch syntax kernel<<<gridDim, blockDim>>>(args) names exactly those two levels.

The hierarchy is not bureaucracy — it encodes the hardware contract:

threadone lane, own registersprivate computationsee another thread's registers
warp (32)the issue unitshuffle registers (__shfl_*_sync), votediverge for free
block (≤1024)one SM, never splitshare SMEM, barrier with __syncthreads()talk to other blocks*

The starred rule is the deep one: blocks must be independent. The scheduler assigns blocks to SMs in any order, as capacity frees — that's precisely what lets the same binary saturate a laptop GPU with 20 SMs and an H100 with 132. The price of that portable scalability is that blocks can't wait on each other within a kernel; if you need a global barrier, you end the kernel and launch another (kernel boundaries are grid-wide barriers). (*Cooperative groups and Hopper's thread-block clusters carve out narrow exceptions — clusters let a few blocks on adjacent SMs share distributed SMEM — but the default model is strict independence.)

Your first real kernel, every line explained

// ---------- device code ----------
__global__ void vecAdd(const float* A, const float* B, float* C, int n) {
    // Recover THIS thread's global index from its coordinates:
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n)              // guard: the last block may overhang n
        C[i] = A[i] + B[i]; // each thread does ONE element
}

// ---------- host code ----------
int n = 1<<20;                                   // 1M floats
float *dA, *dB, *dC;
cudaMalloc(&dA, n*sizeof(float));               // allocate on GPU (HBM)
cudaMemcpy(dA, hA, n*sizeof(float), cudaMemcpyHostToDevice);  // over PCIe/NVLink
// ... same for B, C ...

int block = 256;                                 // threads per block (8 warps)
int grid  = (n + block - 1) / block;             // ceil-div: 4096 blocks
vecAdd<<<grid, block>>>(dA, dB, dC, n);          // launch is ASYNCHRONOUS
cudaDeviceSynchronize();                          // host blocks until GPU done

Read the index line until it's reflexive: blockIdx.x (which block am I in) times blockDim.x (how big is a block) plus threadIdx.x (where am I inside my block). That one expression is how a million logical threads each find their one element of work. Note also what the host code reveals: the GPU has its own memory — nothing computes until you've explicitly shipped data into HBM — and launches are asynchronous, queued onto a stream while the CPU runs ahead.

One idiom upgrade makes it production-grade — the grid-stride loop, which decouples grid size from problem size (launch enough blocks to fill the machine; each thread handles multiple elements):

__global__ void vecAddGS(const float* A, const float* B, float* C, int n) {
    int stride = gridDim.x * blockDim.x;             // total threads in flight
    for (int i = blockIdx.x*blockDim.x + threadIdx.x; i < n; i += stride)
        C[i] = A[i] + B[i];
}

Second kernel: naive matmul — and its built-in doom

Now 2D indexing, and a kernel whose arithmetic we can audit. One thread computes one element of C = A·B (all N×N, row-major):

__global__ void matmulNaive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < N) {
        float acc = 0.f;
        for (int k = 0; k < N; ++k)
            acc += A[row*N + k] * B[k*N + col];   // 2 loads per FMA ← the crime
        C[row*N + col] = acc;
    }
}
// launch: dim3 block(16,16);  dim3 grid((N+15)/16, (N+15)/16);

Audit the inner loop: every iteration does one FMA (2 FLOPs) and two 4-byte global loads (8 bytes). Arithmetic intensity = 2/8 = 0.25 FLOP/byte. Your roofline lesson says an H100 needs ~295 FLOP/byte (BF16) to leave the memory-bound region — this kernel is three orders of magnitude short. It will crawl at a few percent of peak no matter what else you do, because each thread re-fetches from HBM values that its neighbors just fetched too: every element of A and B is loaded N times across the grid. The entire point of Chapter II is fixing exactly this, by staging tiles in shared memory so each element is fetched from HBM once and reused.

04 The engine room

Latency hiding and occupancy: how the trick actually works

Return to the founding bet with mechanism in hand. A global load costs ~400–800 cycles. When warp 7 issues that load, the scheduler doesn't wait — next cycle it issues an instruction from warp 12, then warp 3, round-robin among every resident warp whose next instruction is ready. The switch costs zero cycles because nothing is saved or restored: all 64 warps' registers live simultaneously in that huge 256 KB register file. (Contrast a CPU context switch: microseconds of state shuffling.)

Occupancy quantifies the fuel: resident warps per SM ÷ the max (64). What limits it is a resource-partitioning problem — each SM's fixed pools get divided among blocks:

  • Registers: 65,536 per SM. If your kernel uses 64 registers/thread → 1,024 threads max → 50% occupancy, from registers alone.
  • Shared memory: a block asking 48 KB when the SM has 228 KB → ≤4 blocks resident, whatever else is free.
  • Block size: 1,024-thread blocks give the scheduler coarse, clumsy units; 128–256 (4–8 warps) usually packs better.
The classic misconception Occupancy is not the goal; it's a means of hiding latency, and 100% is rarely optimal. Past the point where latency is covered, extra resident threads just shrink each thread's register budget. Highly-tuned kernels (CUTLASS GEMMs, FlashAttention) often run at 25–50% occupancy deliberately — fewer threads, each fat with registers and instruction-level parallelism, can beat many thin ones. What you actually maximize is issue-slot utilization; occupancy is one lever among several (ILP within a thread is another).

05 Down to the metal

What the machine really runs: PTX and SASS

Your CUDA C++ compiles twice. nvcc first lowers it to PTX — a virtual assembly, a stable ISA that abstracts over GPU generations (the same PTX from your tensor-core chapter: mma.sync.aligned…, tcgen05.mma). Then ptxas compiles PTX to SASS, the real, undocumented, architecture-specific machine code (sm_80 Ampere, sm_90 Hopper, sm_100 Blackwell) — where actual registers are allocated and instructions scheduled. Binaries usually embed both: SASS for the arches you compiled for, PTX so the driver can JIT-compile for GPUs that didn't exist when you shipped. That two-stage design is the CUDA moat's technical core — twenty years of software targets a stable PTX while the silicon underneath churns.

# see the intermediate + real ISA for yourself
nvcc -arch=sm_90 -ptx  kernel.cu     # emit PTX (readable, virtual)
nvcc -arch=sm_90 -cubin kernel.cu && cuobjdump -sass kernel.cubin   # real SASS
nvcc --ptxas-options=-v kernel.cu    # registers/SMEM per thread — your occupancy inputs

That last flag closes the loop on this chapter: ptxas -v prints exactly the register and shared-memory counts that determine occupancy. When you profile in Nsight Compute during the hardware capstone, the counters you'll read — issue-slot utilization, warp stall reasons, achieved occupancy — are precisely the quantities this chapter defined.

Q1 What is the GPU's fundamental strategy for dealing with memory latency?

Hide, don't avoid. A global load costs ~400–800 cycles and the GPU accepts it. The die is spent on lanes and a huge register file instead of caches/control; with up to 64 warps resident per SM, the scheduler always has ready work, and switching is free because nothing is saved or restored. That's also why oversubscription — far more threads than lanes — is a requirement, not a nicety.

Q2 Why is if (threadIdx.x % 2 == 0) a performance disaster while if (blockIdx.x == 0) is free?

The unit that must agree is the warp. SIMT issues one instruction for 32 lanes. If lanes disagree at a branch, the warp runs each path in turn with the other side's lanes masked idle — %2 makes that happen in every warp (up to 1/32 throughput worst-case across many branches). Conditions uniform across a warp (whole blocks, or threadIdx ranges aligned to 32) never split. Compilers also predicate tiny branches, executing both sides cheaply without a real branch.

Q3 Why must thread blocks be independent (no inter-block sync mid-kernel)?

Independence buys portable scalability. The hardware drops blocks onto SMs in unspecified order; if block 5 could wait on block 900, a small GPU that hasn't scheduled block 900 yet would deadlock. So blocks share nothing mid-flight (SMEM and __syncthreads are intra-block), and a kernel boundary is your grid-wide barrier. Cooperative groups and Hopper's block clusters are narrow, opt-in exceptions.

Q4 The naive matmul does one FMA and two 4-byte global loads per inner iteration. What does that imply?

Audit the loop, know the fate. 0.25 FLOP/byte sits three orders of magnitude below the H100's compute-bound threshold, so the kernel crawls at a few percent of peak regardless of launch configuration. The waste is redundant traffic: neighboring threads fetch the same rows/columns from HBM over and over. The fix — staging tiles in shared memory for reuse — is Chapter II's centerpiece.

Q5 Why is 100% occupancy not the goal?

Occupancy is fuel, not the destination. The real target is a never-idle issue slot. Once resident warps suffice to cover stalls, extra occupancy costs registers (SM pools are fixed: 64K registers, 228KB SMEM split among blocks) and can slow things down. CUTLASS/FlashAttention-class kernels deliberately trade occupancy for register-heavy threads with high instruction-level parallelism.

Q6 What are PTX and SASS?

Compile twice, run anywhere (on NVIDIA). nvcc lowers C++ to PTX (virtual, documented, stable across generations — where instructions like mma.sync and tcgen05.mma live), and ptxas lowers PTX to SASS (real, undocumented, per-sm_XX, where registers get allocated). Shipping PTX lets old binaries JIT onto new GPUs — two decades of software keeps working while silicon churns, which is much of why the moat holds.
Takeaway

A GPU is a throughput machine: thousands of thin lanes fed by a scheduler that hides 500-cycle memory stalls under other warps' work, fueled by oversubscription and a register file big enough that switching is free. You program it as scalar threads, but the machine runs 32-wide warps — so divergence, block independence, and occupancy aren't API trivia, they're the hardware showing through. And one audit of a naive matmul's inner loop (0.25 FLOP/byte) tells you its fate before you ever run it — which is why Chapter II is about memory.
