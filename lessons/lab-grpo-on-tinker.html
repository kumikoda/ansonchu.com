Lab — GRPO on Tinker

Theory into a real run. Tinker is a managed harness: it owns the infrastructure — distributed GPUs, the model’s forward/backward — and hands you the algorithm. Which means the GRPO loop from Lesson 5 becomes about thirty lines, and the only interesting parts are the ones you already understand.

01 The harness, abstracted

You keep the algorithm; it takes the infra

Recall the harness from branch C — the orchestration layer around training. Tinker is that layer, productized. You write a normal Python loop on a CPU; Tinker runs the heavy compute on its distributed GPUs. It exposes a handful of primitives and gets out of your way. It’s LoRA-based (you train small adapters, not full weights), supports models from ~1B up, and ships a “cookbook” of reference loops.

The split that matters Tinker’s job: the forward/backward of the LLM, distributed training, scheduling, checkpoints. Your job: the data, the reward/environment, the advantage, the loss — i.e. the RL algorithm itself. That boundary is the whole pitch: you keep the ~10% that’s creative and skip the 90% that’s infrastructure plumbing.

03 The loop

GRPO in ~30 lines

Here’s the whole thing in the cookbook’s shape. Rose lines are Tinker’s infra; amber lines are your algorithm — note how little of it there is, and that you’ve already learned every amber line.

grpo_loop.py · illustrativeimport tinker
from tinker import types

sc = tinker.ServiceClient()
training = sc.create_lora_training_client(
    base_model="Qwen/Qwen3-4B-Base", rank=32,   # LoRA adapters, not full weights
)

for step in range(N):
    # 1 · ROLLOUTS — current policy samples G completions/prompt
    sampler = training.save_weights_and_get_sampling_client()       # tinker
    batch = []
    for p in sample_prompts(pool):
        outs = sampler.sample(                                  # tinker
            prompt=p, num_samples=G,
            sampling_params=types.SamplingParams(temperature=1.0),  # T>0 = exploration!
        )
        rewards = [verify(p, o) for o in outs]              # YOUR environment
        advs    = compute_group_advantages(rewards)          # YOUR algorithm ← exercise
        batch += [make_datum(p, o, adv) for o, adv in zip(outs, advs)]

    # 2 · GRADIENT + UPDATE — tinker does the heavy lifting
    training.forward_backward(batch, loss_fn="importance_sampling")  # tinker
    training.optim_step(types.AdamParams(learning_rate=1e-5))     # tinker

    if step % 50 == 0:
        training.save_state(...)                                  # tinker
Read it against Lesson 5 Sample a group → verify → normalize within the group → policy-gradient update with the clipped/importance-weighted loss. That’s GRPO, line for line. Tinker contributed zero of the algorithm — it only spared you the distributed forward/backward. 04 Your exercise

Implement the one amber line

Task

Write compute_group_advantages(rewards) — the GRPO core. Input: a list of G scalar rewards for one prompt’s group. Output: the group-relative advantage for each. Then answer: what happens to the gradient when every reward in the group is identical, and why does that matter for which prompts you keep?

REVEAL Solution & the gotcha ▸ 
import statistics
def compute_group_advantages(rewards):
    mu    = statistics.mean(rewards)
    sigma = statistics.pstdev(rewards) or 1.0   # guard σ=0
    return [(r - mu) / sigma for r in rewards]

The gotcha: if all G rewards are equal (all correct, or all wrong), then every r − μ = 0, so every advantage is 0, so forward_backward produces a zero gradient — that step taught the model nothing. This is the dead-group insight from Lessons 5–6 made concrete: GRPO only learns from prompts where the group disagrees. In a real Tinker run you’d filter or curriculum your prompt pool to the learnable band (pass-rate roughly 0.2–0.8) so you’re not burning rollouts on unanimous groups. The or 1.0 guard exists precisely to avoid dividing by a zero std on those dead groups.

Q1 Which Tinker primitive performs the rollout phase of GRPO?

sample(). Rollouts = generating the G completions per prompt with the current policy. That's sample(), run with temperature > 0 so the group is diverse. forward_backward and optim_step come after you've scored those completions and built advantages.

Q2 In the GRPO-on-Tinker loop, which part is yours — not Tinker's?

The reward + advantage — the algorithm. Tinker owns infra: the model's forward/backward, distribution, scheduling, the optimizer mechanics. You own the parts that define your method: what counts as correct (verifier) and how rewards become a learning signal (advantage + loss). That split is the entire point of the abstraction.

Q3 Tinker uses LoRA under the hood. What does that mean for your run?

Small adapters, frozen base. LoRA trains low-rank add-on matrices instead of all the weights — far cheaper, tens of MB to store, and it lets Tinker share one GPU pool across many runs. For you it means cheap, fast experiments; the trade is that pure-LoRA RL can sometimes underperform full fine-tuning at the very frontier, but for learning and most runs it's more than enough.

Q4 A prompt's group of 8 all get reward 1 (all correct). What does forward_backward see for those completions?

Zero gradient. All rewards equal → every (r − μ) = 0 → all advantages 0 → nothing to learn from this prompt this step. (And σ = 0, which is why you guard the division.) This is the dead-group insight made real: GRPO learns only where the group disagrees, so you curriculum your prompt pool to the learnable band instead of burning rollouts on unanimous groups. Same as "all wrong," by the way — both tails are dead weight.

Takeaway

Tinker turns GRPO into the three lines you understand plus one you write. It owns the forward/backward and the cluster; you own the verifier and the advantage. The algorithm was never the hard infrastructure part — and now you don’t have to touch the infrastructure to run the algorithm.
