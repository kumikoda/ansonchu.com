RL Environments

In your gym days the environment was a simulator with step(). For LLMs it spans a huge range: for single-turn math it shrinks to just a verifier; for agentic tool-use it becomes a stateful world with real dynamics — and your Lesson 1 MDP machinery roars back to life.

01 Your gym muscle memory, remapped

The same interface, new contents

SB3 trained you on reset() and step(). The abstraction survives intact for LLM-RL — only what flows through it changes:

gym → llm-rl, single-turn // classic gym　obs = env.reset();　obs, r, done = env.step(a)
// llm-rl　　　prompt = env.reset();　r, done = env.step(completion)
// single-turn: done is True after one step — a bandit

A growing ecosystem of LLM “environment” libraries wraps exactly this — a prompt source plus a scoring function behind a gym-like API — so a math task, a code task, and a tool-use task all present the same surface to the trainer. The trainer samples, the env scores, the loop turns.

The conceptual collapse In single-turn RLVR there’s no transition function worth the name: one action ends the episode, so discounting and multi-step credit assignment barely matter. This is why GRPO can treat a whole completion as one action with one advantage — the environment has no dynamics to assign credit across.

02 The heart of it

The verifier is the environment

For single-turn RLVR, all the engineering is in the checker. Three common kinds, increasingly powerful and increasingly gameable:

Every verifier is a reward-hacking surface A weak exact-match extractor can be fooled by an answer that prints many candidates; weak unit tests can be passed by hardcoding outputs or detecting the test harness. The policy will find these — that’s what optimization does. Verifier hardening is not a side task; it’s the core of environment design.

03 Infra reality

Execution means sandboxing

The moment your reward runs model-generated code, the environment has to execute untrusted code thousands of times per training step — safely, with timeouts and resource caps, in parallel. This is real infrastructure, and it’s squarely in your wheelhouse.

04 The hard case

Multi-turn: the MDP comes back

Tool use, agentic coding, web tasks, games — here the model acts, the environment responds, and the next action depends on that response. Now you have real state, real dynamics, and usually a single sparse reward at the very end of a long trajectory. Everything from Lesson 1 returns: horizon, discounting, credit assignment — and the partial-observability flag, because the model only sees observations, not the environment’s full state.

a multi-turn trajectoryobs₀ → act₁ → obs₁ → act₂ → obs₂ → … → act_T → R (only at the end)
This is your Dota ambition, formally A sanctioned Bot API is a classic stateful environment: the agent observes game state, emits actions, the world advances. That puts you back in full-MDP territory — long horizons, sparse win/loss reward, brutal credit assignment over a 45-minute episode — which is exactly why it’s a research-grade sandbox and not a weekend project. The single-turn RLVR skills transfer, but the credit-assignment problem is a different beast.

05 Quiz · three

Check yourself

Q1 SOLVE Why is single-turn RLVR closer to a contextual bandit than a full MDP — and what specifically changes when you go multi-turn agentic? ▸

Single-turn: the episode is one action (the whole completion) followed immediately by a terminal reward. There’s no state transition the agent influences across steps, so there’s nothing to discount and no inter-step credit to assign — the defining features of a contextual bandit. That’s why GRPO can attach one advantage to an entire completion.

Multi-turn: actions now change the environment’s state, and later observations depend on earlier actions. Discounting and horizon (γ) become meaningful again; reward is typically sparse and terminal, so you must assign credit backward across many turns; and you’re usually in a POMDP because the model sees observations, not full state. The MDP machinery from Lesson 1 that single-turn let you ignore is suddenly load-bearing.

Q2 SOLVE A code-RL run shows steadily rising reward, but spot-checking the code, quality isn’t improving. What verifier failure modes top your suspect list? ▸

Classic reward hacking against a weak environment. Suspects: (1) the model learned to print or hardcode the expected outputs rather than compute them — weak tests that only check stdout; (2) test-harness detection — special-casing inputs that appear in the visible tests; (3) exploiting under-specified tests that pass trivially (e.g. empty edge cases, no hidden tests); (4) exit/timeout gaming — returning early or manipulating the harness; (5) format/extraction exploits if partial credit is parsed loosely.

The fix is environment-side, not policy-side: held-out hidden tests, stronger and adversarial test suites, input randomization, and sandbox controls that block harness inspection. The reward went up because the verifier was beatable — exactly what optimization is for.

Q3 SOLVE In single-turn math RLVR vs SWE-bench-style agentic RL, where’s the wall-clock bottleneck — and why does it move? ▸

Math RLVR: the verifier (parse + compare) is microseconds; the cost is almost entirely generation — sampling G completions per prompt on a big model. The bottleneck is the policy’s decode, so inference throughput (batching, KV-cache efficiency, GQA) dominates.

Agentic code: the environment step itself becomes expensive — spinning up a repo, installing deps, running a full test suite in a sandbox, possibly over many turns. Now you’re bottlenecked on sandbox throughput and the multi-turn rollout length, not just decode. Parallel/warm-pooled sandboxes and async environment execution become the thing you optimize. The bottleneck moves from “generate fast” to “execute the world fast.”

Takeaway

“Environment” spans a spectrum: a single verifier for math, a sandbox for code, a stateful world for agents. Single-turn lets you ignore dynamics; multi-turn drags the whole MDP back in. And every verifier is something the policy will try to hack — designing it well is the real work.
