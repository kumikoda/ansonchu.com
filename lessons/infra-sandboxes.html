Sandboxes

The moment your reward or your agent runs model-generated code, you’re executing software no human reviewed, at scale, that might be hostile. The sandbox is the wall between that code and everything you care about — and choosing the wall is a real engineering decision, not a checkbox.

01 Why this is its own problem

The threat model is unusual

A coding-agent sandbox isn’t a general container — it’s built around a specific threat: the code was not written by a human, cannot be reviewed before running, and may be destructive, resource-hungry, or actively malicious. And it runs at a scale that’s easy to underestimate — one provider went from tens of thousands of sandbox sessions a month to roughly fifteen million in a year, with a large share of big enterprises now running agent workloads. Every reward that executes code, every coding agent, every RL rollout that runs tests is a sandbox invocation.

The asymmetry In ordinary deployment you trust your own code and defend the perimeter. Here the call is coming from inside the house — your own system is generating and running the untrusted code on purpose. So isolation can’t be an afterthought bolted to the edge; it has to wrap every single execution.

03 Best practices

The non-negotiables

Hardware-level isolation (microVM) for untrusted code. Hard resource caps and timeouts so a runaway script can’t burn your budget. No network by default — outbound access is an exfiltration path; allow-list if you must. And two that decide your throughput rather than your safety:

Q1 For genuinely untrusted, model-generated code, which isolation is recommended — and why?

microVM. Plain containers share the host kernel, so a kernel exploit escapes to the host. A microVM gives the workload its own kernel behind hardware virtualization — the strongest boundary, and the recommended choice for code you can't trust. gVisor (user-space kernel) is a middle option; containers are for trusted code only.

Q2 Why is sandbox snapshot-restore such a big deal for multi-turn agents?

State persistence, cheaply. A multi-turn agent installs packages, writes files, and accumulates state across turns. Re-initializing the whole sandbox each turn wastes hundreds of ms. Snapshot-restore (Firecracker: ~5–30ms) preserves memory + filesystem and resumes near-instantly — the operational foundation for SWE-bench-style harnesses where context builds over dozens of tool calls.

Q3 In agentic/code RL, where does wall-clock time most often go — and what follows from that?

The sandbox step. Unlike a math check (microseconds), running a repo's test suite in isolation is slow and often dominates the rollout. So sandbox throughput — parallelism, warm pools, snapshot-restore — directly caps how many rollouts/hour you get, which caps how much RL you can afford. It's the bottleneck that moves from "generate fast" to "execute the world fast."

Q4 You need GPU access inside the sandbox. Which isolation choice is affected, and how?

It's a real constraint. gVisor's user-space kernel intercepts GPU calls at a point that blocks direct PCIe passthrough, so it generally can't give a sandbox real GPU access. Firecracker's hardware-virtualization path supports VFIO device passthrough, giving near-native GPU performance inside the microVM. So "I need GPU in the sandbox" pushes you toward Firecracker (or platforms that expose GPUs explicitly), not gVisor-based options.
Takeaway

The call is coming from inside the house — you generate and run untrusted code on purpose, so isolation wraps every execution. microVMs for the strong boundary, warm pools and snapshots for the throughput, and remember: in code-RL the sandbox is usually the bottleneck, not the model.
