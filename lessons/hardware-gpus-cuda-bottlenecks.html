The Machine Underneath

Every architecture trick you just learned — KV compression, FlashAttention, MoE — exists to dodge one physical fact: on a modern accelerator, moving data is far more expensive than computing on it. To reason about ML systems you have to reason about the silicon. Here’s the machine, its bottleneck, and why “FLOPs are cheap, bytes are dear.”

01 What a GPU is

Thousands of cores, fed by HBM

A GPU is a throughput machine: many streaming multiprocessors (SMs), each packed with cores — and crucially Tensor Cores, dedicated units that do small matrix multiply-accumulates in one shot. That’s where the headline FLOPs come from, and why everything is cast as matmuls. The cores are fed from HBM (high-bandwidth stacked memory) — an H100 has ~80GB, newer parts more — through the cache hierarchy above.

The number that explains the era Tensor-core compute has grown far faster than memory bandwidth. A modern GPU can do hundreds of FLOPs in the time it takes to fetch a single byte from HBM. So unless an operation reuses each loaded byte for hundreds of arithmetic ops, the cores sit idle waiting on memory. That ratio — arithmetic intensity, FLOPs per byte — decides whether you’re compute-bound or memory-bound, and it’s the master variable of ML systems.

02 The one mental model

Compute-bound vs memory-bound

Every kernel is limited by one of two ceilings: how fast the cores can compute, or how fast memory can feed them. The roofline says which. Big dense matmuls (lots of reuse) are compute-bound — the good regime, cores busy. Operations that stream a lot of data and do little math per byte are memory-bound — cores starving.

Now the architecture tricks make sense FlashAttention: stop writing the N² matrix to HBM → cut memory traffic. KV compression (GQA/MLA): the cache you re-stream every decode step is smaller → less memory traffic. MoE: more parameters but only top-k active → FLOPs stay bounded. Every one of them is buying back arithmetic intensity. The model designers are programming around this roofline whether they say so or not.

03 The moat and the network

CUDA, and the bottleneck between chips

CUDA is NVIDIA’s programming model — and its real moat. The hardware advantage is real but copyable; the decade of libraries (cuDNN, cuBLAS, the whole kernel ecosystem, things like FlashAttention written for CUDA first) is what locks people in. AMD’s answer is ROCm; Google’s stack compiles through XLA. The consensus: the CUDA moat is widest for training and narrowest for inference, which is exactly where challengers attack.

And once one chip isn’t enough, a new bottleneck appears: the network between chips. Inside a node, GPUs talk over fast NVLink; across nodes, over InfiniBand/Ethernet — an order of magnitude slower. Distributed training is a constant fight to keep the collective communication (all-reduce of gradients, all-to-all for MoE) from dominating, which is why systems like NVLink-connected 72-GPU racks exist: make a big group of chips behave like one.

This is your harness lesson, one layer down Weight sync and the actor-learner shuffle from the harness lesson are this — inter-chip bandwidth. Disaggregation (separate prefill/decode or generate/train pools) is roofline-aware scheduling: put the memory-bound work and the compute-bound work on hardware sized for each. The whole RL-systems stack is, at the bottom, an exercise in respecting the memory and network walls.

Q1 What is "arithmetic intensity," and why is it the master variable?

FLOPs per byte. Modern GPUs can do hundreds of FLOPs in the time it takes to fetch one byte from HBM. So if an operation doesn't reuse each loaded byte enough, the cores idle waiting on memory. Arithmetic intensity — math per byte moved — is what places an op on the roofline and decides its ceiling. It's the single most useful number in ML systems.

Q2 Why is autoregressive decode memory-bound while prefill is compute-bound?

Reuse. Prefill processes the whole prompt at once — large matmuls that reuse loaded weights across many tokens (compute-bound, efficient). Decode generates one token per step, so it re-reads all the weights (and the KV cache) to produce a single token — tons of memory traffic, little math (memory-bound). That's why generation is slow and why batching many requests together helps amortize the weight loads.

Q3 FlashAttention, GQA/MLA, and MoE share a hidden common purpose. What?

Buying back arithmetic intensity. FlashAttention avoids writing the N² matrix to HBM; GQA/MLA shrink the KV cache that decode re-streams; MoE adds parameters but keeps active FLOPs bounded. Different mechanisms, one target: do less memory movement per unit of useful compute. The architecture designers are programming around the roofline.

Q4 What is the CUDA "moat," really?

Software, not just silicon. Competitors can match raw FLOPs and HBM, but CUDA's libraries, kernels, and tooling — written CUDA-first for years — are the real lock-in. AMD's ROCm and Google's XLA are the alternatives. The moat is widest for training (complex, custom kernels) and narrowest for inference (simpler, more standardized), which is exactly where Groq, Cerebras, TPUs and others attack.
Takeaway

A GPU is thousands of matmul cores starved by a memory hierarchy — so the master variable is arithmetic intensity, FLOPs per byte, and the master question is "memory-bound or compute-bound?" Decode is memory-bound, the CUDA moat is software, and the network between chips is the next wall. Every architecture trick you know is a move in this game.
