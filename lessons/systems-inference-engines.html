The Inference Engine

A trained model is useless until something serves it fast. Naive generation leaves a $30,000 GPU mostly idle — decoding one token at a time, stalling on memory. Inference engines like vLLM and SGLang exist to fix exactly that: squeeze maximum tokens out of every GPU-second. They’re also the rollout engine inside your RL harness, so their speed is your training speed.

01 The problem

Why generation wastes a GPU

Two structural facts from your KV-cache and hardware lessons make serving hard. First, decode is memory-bound: each new token requires re-reading the whole model plus the growing KV cache, doing tiny compute per byte moved — the GPU’s math units starve. Second, the KV cache is enormous and variable: it grows with every token, differs per request, and must live in precious HBM. Pile on requests of different lengths arriving asynchronously, and the classic approach — static batching — falls apart: the whole batch waits for its slowest sequence while finished ones leave dead slots.

02 vLLM’s idea

PagedAttention: treat the KV cache like RAM

The second half. Storing each sequence’s KV cache in one big contiguous block wastes 60–80% of GPU memory to fragmentation and over-reservation — you must reserve for the longest possible output. PagedAttention borrows the oldest trick in operating systems: virtual memory. Break the KV cache into small fixed-size blocks that can sit anywhere in HBM, with a page table mapping logical positions to physical blocks.

This is your harness, sped up In a GRPO run you sample many rollouts per prompt — exactly the “parallel samples share a prefix” case PagedAttention nails. vLLM is the generation half of most RL harnesses, so its tokens/sec is your rollout throughput, which dominates RL wall-clock. Faster engine → faster RL.

03 SGLang’s idea

RadixAttention: stop regenerating the same prefix

SGLang starts from the same paged memory, then adds one sharp insight: don’t throw the KV cache away when a request finishes. It keeps an LRU cache of computed KV in a radix tree; when a new request arrives, it prefix-matches against the tree and reuses the cached KV for any shared prefix. If vLLM asks “how many tokens per second can I generate?”, SGLang asks “how many tokens can I avoid regenerating?”

04 The rest of the toolbox

Speculation, chunking, and splitting the phases

Modern engines layer on several more tricks, and the two leaders have largely converged — both now support all of these:

Speculative decoding. A small, cheap “draft” model proposes the next k tokens; the big model verifies them in a single parallel pass and accepts the longest correct run. Fewer expensive forward passes → lower latency, same output distribution.

Chunked prefill. Long prompts can hog the GPU and stall everyone’s decode. Breaking the prefill into chunks and interleaving it with ongoing decode smooths tail latency.

Prefill/decode disaggregation. The deepest idea, and one you’ve been circling at work: prefill is compute-bound, decode is memory-bound, and co-locating them makes each interfere with the other. Split them onto separate GPU pools, each tuned for its phase, and stream the KV cache between.

The landscape, briefly vLLM — the broad, general-purpose default; widest model support. SGLang — prefix-heavy, agentic, and structured workloads; now a major force (HuggingFace’s TGI went into maintenance mode in late 2025, leaving SGLang as its main successor). TensorRT-LLM — NVIDIA’s engine, the lowest latency on NVIDIA silicon, but it pays a 25–40-minute per-model engine compile step and less flexibility. The trend is convergence: feature sets, kernels (FlashAttention/FlashInfer), and tricks are increasingly shared, so the choice is now per-workload, not absolute.

Q1 What does continuous batching fix versus static batching?

Iteration-level scheduling. With requests of different lengths, a static batch stalls on its longest sequence while finished ones leave dead slots. Continuous batching (Orca → vLLM) schedules per decode iteration: retire completed sequences and admit waiting ones immediately, so the batch stays saturated and the GPU rarely idles.

Q2 What is PagedAttention and what does it borrow from?

Virtual memory for KV. Contiguous KV allocation forces reserving for the longest possible output, wasting most of the memory. PagedAttention pages the cache into fixed-size blocks placed anywhere, with a page table — slashing fragmentation so many more sequences fit, and letting blocks be shared (parallel samples, common prefixes) via copy-on-write.

Q3 What's SGLang's RadixAttention insight, and when does it shine?

Avoid regenerating prefixes. RadixAttention keeps an LRU radix tree of computed KV and prefix-matches new requests against it, reusing cached computation for any shared prefix. Where prefixes repeat — shared system prompts, few-shot blocks, multi-turn chat, branching agent trees — it can lift throughput 30%+ over vLLM at no app-code cost.

Q4 Why disaggregate prefill and decode onto separate pools?

The roofline as a topology. The two phases have opposite bottlenecks — prefill saturates compute, decode saturates memory bandwidth — so running them together makes each degrade the other's tail latency. Disaggregation (Splitwise, DistServe) gives each its own tuned pool and streams the KV between, reporting large goodput and latency-variance wins.

Q5 How does speculative decoding speed things up without changing the output?

Draft-then-verify. Decode is memory-bound, so a single forward pass can cheaply check several proposed tokens at once. A small draft model guesses k tokens; the target model verifies them in parallel and keeps the longest prefix that matches what it would have produced — preserving the exact output distribution while cutting the number of slow target passes.
Takeaway

Inference engines exist to keep a starving, memory-bound GPU saturated. vLLM did it with continuous batching plus PagedAttention (virtual memory for the KV cache, ~60–80% waste → under 4%); SGLang added RadixAttention to reuse shared prefixes instead of regenerating them. Layer on speculative decoding, chunked prefill, and prefill/decode disaggregation — your roofline lesson made into a deployment. And since vLLM is the rollout engine in your RL harness, all of this is also how fast you can train.
